# MASTER TECHNICAL DEVELOPMENT SPECIFICATION
## RazorRecover AI — AI Revenue Recovery Agent
### Implementation-Ready Architecture Baseline (Sections 1–5)

---

## 0. Revision Notes — What Changed From v1.0 and Why
The core philosophy is: **The LLM proposes, deterministic policy code decides, and only the tool executor acts.**

**Non-negotiable rule**: The LLM proposes; deterministic application code decides whether an action is allowed; only the tool executor performs an approved action. No code path may skip the Policy Engine to call a Razorpay-mutating tool directly.

---

## 1. Product Definition

### 1.1 Problem
Merchants lose revenue when payments fail and recovery is manual or based on simplistic retry rules. RazorRecover AI identifies recovery opportunities, analyzes customer/payment context, recommends an action, applies guardrails, executes approved recovery actions, and measures outcomes.

### 1.2 Primary User Journey
Failed payment → event ingestion → case creation → context aggregation → risk analysis → AI recommendation → policy decision → optional human approval → controlled action → outcome tracking → dashboard.

### 1.3 MVP Outcome
- A failed payment can enter the system through Razorpay Test Mode or a controlled fixture and appear as a recovery case.
- AI produces a structured recommendation with probability, confidence, action, reason, and risk signals.
- Policy can ALLOW, DENY, or require HUMAN_APPROVAL.
- An allowed case can create a Razorpay Payment Link and record a notification.
- The complete decision chain is visible in the case timeline.
- Dashboard metrics show failed revenue, recoverable revenue, recovered revenue, recovery rate, pending cases, and escalations.
- Duplicate webhooks, invalid signatures, malformed AI output, provider errors, and already-recovered payments are handled safely.
- A merchant owner logs in and sees only their own data (Auth is P0 in this revision).

## 2. Architecture Principles

| Principle | Implementation Rule |
| :--- | :--- |
| **Controlled autonomy** | AI recommends; it cannot bypass policy. |
| **Single source of truth** | Payment state always comes from backend/provider data, never inferred from AI output. |
| **Event-driven** | Webhooks create/advance cases; heavy work runs asynchronously via Celery. |
| **Idempotent** | Webhook events and recovery actions require duplicate protection via unique keys (§17). |
| **Typed contracts** | Pydantic schemas define API/AI/policy/tool contracts; TS types are generated from FastAPI's OpenAPI schema, never hand-duplicated. |
| **Auditability** | Every decision/action is traceable by `correlation_id`, written to `audit_logs` in the same DB transaction as the state change it records. |
| **Fail closed** | Invalid, timed-out, or uncertain states never trigger financial actions — they route to DENY or human review. |
| **Provider abstraction** | Razorpay-specific code stays inside `integrations/razorpay`; no other module imports the Razorpay SDK. |
| **Modular monolith** | One deployable backend; module boundaries enforced by import rules (§5), not network calls. |
| **Observable** | Structured JSON logs, metrics, action status and error categories are first-class (§22). |

| **Validation** | Pydantic v2 | `extra="forbid"` on every schema — unknown fields rejected, not ignored. |
| **ORM** | SQLAlchemy 2.x (async engine) | No lazy-load in request handlers — use `selectinload` explicitly. |
| **Migrations** | Alembic | Autogenerated diffs require manual review; never auto-applied in CI. |
| **Database** | PostgreSQL 16 | JSONB only for AI raw payloads, never for queryable relational fields. |
| **Queue** | Redis + Celery | FIX: Redis is also the Celery result backend — no separate store. |
| **AI** | OpenAI Responses API | Structured Outputs (strict JSON Schema); model IDs pinned via env var (§11). |
| **Payment** | Razorpay SDK/REST adapter | Isolated in `integrations/razorpay/`. |
| **Auth** | JWT (access+refresh) + bcrypt | FIX: moved to P0. Single 'owner' role; RBAC expansion is P2. |
| **Testing** | Pytest + HTTPX + Playwright | Coverage gate ≥80% on `services/`, `policy/`, `ai/schemas.py`. |
| **Quality** | Ruff + Black + ESLint + Prettier | Pre-commit + CI gate; build fails on lint error. |
| **Infra** | Docker + Docker Compose | FIX: `infra/` scoped to `infra/docker/` and `infra/nginx/` only. |
| **CI** | GitHub Actions | `lint` → `unit` → `integration` → `build`, fail-fast order. |

## 5. Backend Architecture — Layering Rules

| Layer | Example | Responsibility |
| :--- | :--- | :--- |
| **Router** | `recovery.py` | HTTP only: parse request, call one service method, return response. No business logic, no DB session logic beyond dependency injection. |
| **Schema** | `RecoveryCaseResponse` | Validation/serialization. `extra="forbid"`. |
| **Service** | `RecoveryOrchestrator` | Business workflow. The only layer allowed to call Policy, AI, and multiple repositories in one operation. |
| **Repository** | `RecoveryCaseRepository` | Database access only. No business rules, no policy checks. |
| **Integration** | `RazorpayClient` | External provider HTTP calls only. Never called directly by a router or the AI layer. |
| **Policy** | `RecoveryPolicyEngine` | Deterministic authorization (§13). Pure function: `(context) → decision`. No I/O. |
| **AI** | `RecoveryReasoner` | Produces a recommendation only (§11–12). Cannot call tools or integrations directly. |
| **Tool** | `CreatePaymentLinkTool` | Validated action execution (§14). The only layer permitted to call integrations for writes, and only after Policy = ALLOW. |
| **Worker** | `AnalyzeRecoveryCaseTask` | Async orchestration entrypoint (§16). Calls services; does not embed business logic itself. |

**Import rule**: `routers → services → {repositories, integrations, policy, ai, tools}`. Reverse imports are forbidden and enforced by an import-linter rule in CI (import-linter or a pytest AST-check).
